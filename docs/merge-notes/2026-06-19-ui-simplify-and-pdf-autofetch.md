## 🧪 PM 需要测试什么

### 测试步骤

1. 启动服务器: `cd backend && python3 main.py`
2. 打开 http://localhost:8000，填 API Key，上传一篇含案例、文章（尤其是只能在 SSRN / ResearchGate 找到全文的文章）的论文
3. 点击 "Check Citations"，等待跑完
4. 观察结果页顶部统计卡片、每条引用卡片的来源展示区、以及"上传源文件"按钮

### 预期结果

- **结果页顶部**：原来"统计卡片区"+"过滤按钮栏"两块重复的东西合并成一个——统计卡片本身现在可以点击当过滤器用（再点一次取消过滤），不再有单独一行过滤按钮
- **引用卡片**：标题栏原来两个来源小标签（PDF 标签 + 来源数据库标签）合并成一个；正文里原来三处重复出现的"来源链接"合并成一条"证据栏"；"Gemini 还看了哪些其他页面"那段默认收起，点开才展开；不适用的"括号说明是否准确" / "页码是否准确"行，如果本来就没有就不再显示空行
- **PDF 自动抓取**：能找到直接 PDF 链接的来源（案例的判决书、文章的开放获取 PDF，包括 SSRN/ResearchGate 上的），现在会先尝试由我们服务器自己下载 PDF、在浏览器里用 pdf.js 抽出正文，再喂给 Gemini 分析——卡片里会出现绿色提示「✓ Full text auto-fetched from the source PDF」，表示这次结论是基于真实正文，不是网页摘要
- **自动抓取失败时**：会安静地退回到原来的网页搜索模式，不会报错打断流程；用户仍可以用"Can't verify? Upload the source"手动上传文件来强制核查
- **核查准确度**：之前那种"只看了第一句就说不支持"的情况应该减少——提示词现在要求 Gemini 先通读全文大意（卡片里会显示"Document covers: ……"一行），再做关键词扫描，最后才下结论

## 📝 已知限制 / 不完美之处

> 这里列出当前版本的局限性，PM 验收时不应该测试这些场景

- [ ] PDF 自动抓取依赖目标网站允许服务器直接下载；如果目标站有强力反爬虫/登录墙（比如部分 SSRN 链接、需要机构权限的 HeinOnline），仍会下载失败，自动退回网页搜索模式
- [ ] 自动抓取只对"看起来是 PDF"的链接生效（按 Content-Type 或文件头 `%PDF` 判断），HTML 落地页不会被抓取解析
- [ ] 本次改动在本地沙箱环境里无法连外网，PDF 自动抓取功能只验证了接口本身的错误处理逻辑（如 404/403 正确返回错误），未做真实下载的端到端验证——**这是 PM 验收时的重点项**
- [ ] 统计卡片改成可点击过滤器后，没有了"全部 (All)"按钮——再点一次已选中的卡片即可取消过滤回到"全部"，PM 验收时确认这个交互是否足够直观
- [ ] 三段式核查提示词是工程层面的改进，没有用真实 API Key 跑过大规模回归，需要 PM 用真实论文多测几篇确认效果
